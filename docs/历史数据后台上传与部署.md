# 历史综测和奖学金：后台上传与服务器部署

本文对应仓库中的历史数据导入功能。更新代码并部署后，超级管理员可在后台自行上传 Excel；不要把学生数据提交到 Git。

## 导入内容和规则

- 超级管理员从“历史数据导入”页面选择 Excel，先预览，再确认导入。
- 大一上总表和大一下总表分别导入各自学期；数据以两张综测总表为准，不用奖学金表覆盖综测分数。导入后先为待发布结果，需要到“发布与公示”执行发布。
- 上传大一上学期年级总表时填写 `2025-2026-1`；上传大一下学期综测总表时填写 `2025-2026-2`。下学期工作簿有公式，系统读取文件中保存的缓存值，上传前应在可信表格软件中确认计算结果并保存。
- 主成绩字段按系统规则四舍五入保留两位；原表精确数值、来源行和公式缓存标记保存在历史来源中。历史表未提供的班级排名、课程明细和分项构成不会被当成真实零分展示。
- 奖学金文件以 `2025-2026` 学年上传。后台按人展示原表奖项和特色工作表对应的项目名单；保留来源，不根据奖学金表的分数重新计算综测，也不声称奖金已发放。
- 导入只匹配系统中已有的学生，并核对学号和姓名；有不匹配的行会阻止确认。已有同学期批次不能覆盖或重复创建；预览报冲突时先停下来核对，不要删除原批次。
- 历史汇总缺少完整课程成绩，不能自动判定奖学金资格；现有计算结果导出模板也不适用于这些汇总记录，请保留原始 Excel 作为档案。

## 一、在服务器拉取代码

项目实际位置不是 `/opt/zongce` 时，下面的路径均按实际情况替换。正式数据通过后台上传，不要把 Excel、数据库、密钥、视频或交付包放入 Git。

在服务器查找已部署服务：

```bash
systemctl cat zongce-backend
```

查看 `WorkingDirectory`、`ExecStart` 和 `EnvironmentFile`。如果服务名称不同，使用实际服务名称。

```bash
cd /opt/zongce
git status --short
git branch --show-current
git remote -v
git rev-parse --short HEAD
```

确认这是正确的项目和远程仓库，并查看服务器上是否有本地修改。如果修改与拉取冲突，先备份并核对，不要用 `git reset --hard` 覆盖服务器文件。先备份本次涉及的现有代码和 schema（不包含环境密钥或数据库）：

```bash
(umask 077; tar -czf /root/zongce-code-before-historical.tar.gz \
  apps/backend/src apps/backend/prisma/schema.prisma apps/frontend/src)
```

确认备份成功、当前在 `main` 分支且远程 `origin` 指向项目仓库后，执行：

```bash
git pull --ff-only origin main
```

如果 Git 提示本地修改、分支分叉或其他错误，先停止并处理，不要强制覆盖。拉取代码不会执行数据库脚本，也不会自动启动服务；继续完成下面的数据库和构建步骤。

## 二、备份数据库并创建历史奖学金表

本功能使用独立表，不覆盖已有的 `ScholarshipAward`。先确认应用实际上连接的数据库主机、端口和库名。服务器已有 MariaDB，不能仅凭 `3306` 判断它是否为当前应用数据库；确认与部署的 Prisma 数据库兼容后再操作。以下 `数据库地址`、`端口`、`数据库用户名`、`数据库名` 都是占位符。

先做数据库备份（密码在提示符输入，不写入命令）：

```bash
(umask 077; mysqldump --single-transaction -h 数据库地址 -P 端口 -u 数据库用户名 -p 数据库名 > /root/zongce-before-historical.sql)
```

确认命令成功且备份文件非空；正式环境应按现有备份制度验证恢复。备份包含学生数据，限制访问，不要上传到 Git。

查询目标库 `Student.id` 的类型、字符集和排序规则，同时检查新表是否已存在：

```bash
mysql -h 数据库地址 -P 端口 -u 数据库用户名 -p 数据库名 -e "SELECT COLUMN_TYPE, CHARACTER_SET_NAME, COLLATION_NAME FROM information_schema.COLUMNS WHERE TABLE_SCHEMA=DATABASE() AND TABLE_NAME='Student' AND COLUMN_NAME='id'; SHOW TABLES LIKE 'HistoricalScholarshipRecord'; SHOW TABLES LIKE 'HistoricalScholarshipImport';"
```

打开仓库中的 SQL 文件，遵照文件开头说明，将 `{{STUDENT_ID_CHARSET}}`、`{{STUDENT_ID_COLLATION}}` 替换为刚才查询到的真实值。也可先复制到 `/root` 再编辑执行，避免修改仓库内的文件：

```bash
cp /opt/zongce/apps/backend/prisma/manual/20261116_historical_scholarship.sql /root/zongce-historical.sql
nano /root/zongce-historical.sql
```

检查 `Student.id` 的类型是否和脚本预期一致。如果有已有同名表、查询不到字段、排序规则不明确或脚本包含其他未替换占位符，先停止并检查，不要删除现有表。

确认 SQL 内容、数据库目标和备份无误，再执行：

```bash
mysql -h 数据库地址 -P 端口 -u 数据库用户名 -p 数据库名 < /root/zongce-historical.sql
```

MySQL 的建表语句会隐式提交；如果脚本执行到一半失败，先检查哪张表已创建及具体原因，不要盲目重跑或删除数据。

不要对现有业务库运行 `prisma db push` 或 `pnpm db:seed` 来部署本功能。

## 三、构建和重启项目

确保使用项目原本的 Node.js 22+ 和 pnpm 11.23.0，并在项目根目录执行：

```bash
cd /opt/zongce
node -v
pnpm --version
```

```bash
pnpm --filter @zc/shared build
pnpm --filter @zc/backend build:image
pnpm --filter @zc/frontend build
```

`build:image` 会重新生成 Prisma 客户端。若提示缺少 `DATABASE_URL`，应按服务器现有部署方式安全地向构建进程提供该变量；不要把其值粘贴到聊天或终端公开日志。命令任一步失败都先停止，检查错误，不要重启到不完整版本。

确保 Nginx 进程可以遍历项目目录并读取生成的前端静态文件；只对前端产物设置读取权限，不要公开上传文件或环境配置：

```bash
chmod o+x /opt/zongce /opt/zongce/apps /opt/zongce/apps/frontend
chmod -R a+rX /opt/zongce/apps/frontend/dist
```

构建通过后重启后端服务（服务名称按实际替换）：

```bash
systemctl restart zongce-backend
systemctl status zongce-backend --no-pager -l
```

确认 Nginx 实际使用的静态目录是本项目的 `apps/frontend/dist`，并检查后端服务日志。无需修改其他网站的 Nginx 或重启 DCDN。

## 四、自己从后台上传

1. 使用**超级管理员**登录，进入“历史数据导入”。
2. 选择大一上总表，填写 `2025-2026-1`，点击预览；核对学生匹配、警告和人数。若有学号/姓名不匹配或已有批次，先解决，不要强行提交。
3. 确认导入后，到“发布与公示”选择该学期并发布。若希望保留原表年级排名，发布时不要开启隐藏前 N 名排名的选项。发布前检查公示期限设置。
4. 对大一下总表重复操作，学期填 `2025-2026-2`。
5. 在“历史数据导入”的奖学金页上传 `奖学金.xlsx`，学年填 `2025-2026`；预览确认后导入。
6. 在“奖学金”页面选择学年，查看每人的奖项和特色项目。没有奖项记录显示为未记录，不自动代表资格审核或发放状态。
7. 用已授权的测试学生账号分别核对两学期查分、排名和原表；管理员核对各奖项名单。请在测试环境或合适时段操作。

本地只读校验中，上学期总表有 987 条、下学期总表有 990 条。正式服务器能否全部匹配，取决于目标库学生档案；上传预览会显示实际结果。
